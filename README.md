# X2 LOTO — ЧҮКӨ Modern 3D

## Назначение сборки

`ЧҮКӨ Modern 3D` — браузерная 3D-игра X2 LOTO на Babylon.js + Havok. Сборка предназначена для размещения на сайте X2 LOTO и подключения к LMS.

Ключевой принцип REAL-режима: **LMS является единственным источником истины для билета, сценария, выигрыша и итогового баланса.** Игра не рассчитывает денежный выигрыш самостоятельно. После получения билета от LMS клиент только визуализирует выданный сценарий.

Текущая интеграционная схема уже реализована в коде:

- статическая HTML/JS-игра, которую удобно размещать отдельным URL и открывать в `iframe`;
- инициализация через `postMessage` (`X2_LMS_INIT`);
- получение session от родительской страницы;
- покупка билета через LMS `PayTicket`;
- REAL / DEMO;
- номиналы;
- баланс;
- локальная история последних билетов;
- автоигра;
- RU / EN / KG / ZH;
- события игры в родительское окно;
- адаптация под desktop / iPhone / Android / in-app browsers.

> Полное ТЗ программисту и порядок подключения: **`INTEGRATION_INSTRUCTION.md`**.  
> Формальный контракт LMS: **`LMS_API.md`**.

В `index.html` сейчас подключаются:

- Babylon.js `9.25.0`;
- Babylon GLTF Loaders `9.25.0`;
- Havok Physics с CDN Babylon.

Для production возможны два варианта:

1. оставить CDN и разрешить эти домены в CSP;
2. положить библиотеки локально рядом с игрой и убрать внешнюю зависимость.

При строгом production CSP второй вариант предпочтительнее.

## Сценарии

Игра поддерживает полный набор сценариев от `0` до `5` выбитых обычных чүкө, а также варианты с ХАНОМ для каждого выигрышного количества от `1` до `5`.

Numeric ID `1..7` сохранены без изменений для обратной совместимости с уже настроенной LMS-интеграцией. Новые варианты `+ ХАН` добавлены новыми ID `8..11`.

| ID | Ключ | Визуальный результат |
|---:|---|---|
| 1 | `ZERO` | выбито 0 |
| 2 | `ONE` | выбито 1 чүкө |
| 8 | `ONE_KHAN` | выбито 1 чүкө + ХАН |
| 3 | `TWO` | выбито 2 чүкө |
| 9 | `TWO_KHAN` | выбито 2 чүкө + ХАН |
| 6 | `THREE` | выбито 3 чүкө |
| 10 | `THREE_KHAN` | выбито 3 чүкө + ХАН |
| 7 | `FOUR` | выбито 4 чүкө |
| 11 | `FOUR_KHAN` | выбито 4 чүкө + ХАН |
| 4 | `FIVE` | выбито 5 чүкө |
| 5 | `FIVE_KHAN` | выбито 5 чүкө + ХАН |

### Важное правило по выплатам

Поле `demoMultiplier` используется **только для локального DEMO/QA** и не является утверждённой таблицей выплат.

Для REAL-режима:

- LMS заранее определяет `scenario`;
- LMS возвращает точный `win`;
- игра не вычисляет денежный выигрыш из количества выбитых чүкө или наличия ХАНА;
- итоговый денежный результат всегда берётся из ответа LMS.

То есть любой из 11 сценариев — это только визуальное описание результата билета, а не формула выплаты.

## REAL: главный цикл раунда

1. LMS/родительская страница инициализирует игру.
2. Игрок выбирает номинал.
3. По кнопке «Новая игра» игра делает `PayTicket`.
4. LMS возвращает `ticketId + scenario + win + balance`.
5. Игра сохраняет `balance` как pending и получает право начать бросок.
6. Игрок бросает САКА.
7. 3D визуализирует сценарий.
8. После завершения анимации показываются `win` и точный `balance`, возвращённый LMS.
9. Игра отправляет `X2_GAME_ROUND_COMPLETE` родительской странице.

Важно: при REAL билет должен быть создан **до броска**, потому что результат уже определён LMS и затем только визуализируется.

## Баланс

В нормальном REAL-потоке игра **не запрашивает баланс отдельным API-вызовом**.

Баланс приходит:

- первый раз в `X2_LMS_INIT.balance`;
- затем в каждом ответе `PayTicket`.

При нажатии «Новая игра» UI оптимистично уменьшает отображаемый баланс на стоимость билета. Если покупка билета не состоялась, сумма возвращается. После завершения раунда устанавливается точный `balance` из ответа LMS.

## Быстрый запуск QA

Текущая сборка имеет локальный mock-режим. Для автономного теста достаточно раздать папку обычным HTTP-сервером (не открывать `file://`).

Для принудительного сценария QA поддерживается query-параметр `scenario`, например:

```text
?scenario=ZERO
?scenario=ONE_KHAN
?scenario=TWO_KHAN
?scenario=10
?scenario=FIVE_KHAN
```

Для production mock необходимо отключить — см. `INTEGRATION_INSTRUCTION.md`.

## Перед production обязательно

- `mock: false`;
- реальный `gameId` в `lms-config.js`;
- реальный URL `PayTicket`;
- ограничить `parentOrigin` / `allowedParentOrigins` конкретными origin;
- проверить CORS / cookies / session header;
- решить, оставляем ли DEMO;
- скрыть/удалить FPS-панель и debug-строку, если они не нужны оператору;
- унифицировать номер версии во всех файлах перед релизом;
- не показывать игроку сырые технические коды из `X2_GAME_ERROR`.

---

## Важное правило по ошибкам

`X2_GAME_ERROR` — канал технической интеграции и телеметрии. Родительский сайт **не должен** показывать игроку `code`, `message`, stack trace или внутренние коды напрямую.

Игроку показываются только нормальные локализованные сообщения интерфейса игры: недостаточно средств, сессия завершена, не удалось начать игру и т.п.

В частности, внутренние визуальные диагностические проверки не должны становиться пользовательскими ошибками. LMS-результат билета остаётся авторитетным.


## Обновление на Samsung / Android и кэш браузера

Сборка **0.13.18** содержит принудительное cache-busting для локальных JS/CSS и самого HTML.
При первом открытии URL автоматически добавляется `?build=0.13.18`. Это сделано потому, что Samsung Internet и ярлык сайта на домашнем экране могут продолжать использовать старый `index.html`, даже если файлы на сервере уже заменены.

После выкладки новой версии программист должен:

1. заменить **весь комплект файлов**, а не только `scenario-config.js`;
2. убедиться, что `index.html` содержит ссылки вида `?v=0.13.18`;
3. открыть игру один раз по новому URL с `?build=0.13.18`;
4. если на устройстве сохранён старый ярлык сайта, удалить его и создать заново после первого открытия новой сборки.

Проверка версии: файл `BUILD.txt` и глобальная переменная `window.X2_CHUKO_BUILD` должны показывать `0.13.18`.
